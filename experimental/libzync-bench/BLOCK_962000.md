## How it works (`prover/methods/guest/src/batch_ecdsa.rs`)

1. **Hook.** `hook/apply_batch_hook.py` adds an `#ifdef HAZYNC_BATCH_ECDSA` hook to libsecp's
   `secp256k1_ecdsa_sig_verify`. It sits after libsecp has checked r,s ≠ 0 and computed u1 = e/s and
   u2 = r/s, and before the ecmult.
2. **Collect pass.** With no hints yet, the guest logs every `(u1, u2, Q, r)` and libsecp verifies as
   normal. `hook/make_batch_hints.py` computes R = u1·G + u2·Q and the verdict for each.
3. **Measured pass.** Each hint is a valid bit plus R.
   - **Bit 0:** libsecp verifies it exactly as before. This is the SwiftSync-shaped part: one bit per
     check.
   - **Bit 1:** the guest checks R is on the curve and that x(R) mod n == r (ECDSA's acceptance test),
     then defers it.
4. **End of chunk.** Σ zᵢu2ᵢQᵢ − Σ zᵢRᵢ + (Σ zᵢu1ᵢ)G = O is checked as one MSM, with 128-bit zᵢ
   from a hash of every deferred tuple. A wrong hint can only fail the chunk (`all_valid = 0`); it
   cannot pass a bad signature.

## The next levers this exposes (not built)

- **Each transaction is deserialised three times and hashed twice per chunk.** That is
  `verify_inputs_batch`, `tx_seqs_batch` and `tx_wtxid_info`, and the last rebuilds a `CTransaction`,
  recomputing the txid and wtxid `verify_inputs_batch` already computed. Returning them from the first
  call removes most of `tx_wtxid_info`: ~80 M, ~9%. Core's code is untouched; it is the call pattern.
- **Journal commit through serde** costs 49 M (~6%). That is the same word-at-a-time pattern
  `agg-readslice` fixed on the read side.
- **Batch per-signature work.** 15.6k per signature in the finish (transcript ~2.7k), plus the hook's
  byte-order conversions (21.6 M). The bench's derived trims put this at ~10–12k.
- **memcpy and paging** (~27% together) are the zero-copy witness question.

# Round 2 — the hashing fix, 16 chunks, and the aggregate (2026-10-28)

## The hashing fix: `tx-once` (`HAZYNC_TX_ONCE=1`, cargo feature `tx-once`)

**What changed.** `verify_inputs_batch_once` in `verify_input.cpp` returns everything the chunk used
to get from three calls: the verdicts, nSequence and version (`tx_seqs_batch`), and the wtxid
(`tx_wtxid_info`). It works from ONE deserialise and ONE `CTransaction`. It uses the same Core
functions; only the call pattern changes.

**Measured on one chunk:** GHOST + batch went from 750.8 M to **664.9 M (−11.4%)**. Against CORE's
3,357.6 M that is **5.05x**.

### ⛔ The straggler: one quadratic-sighash transaction

**Chunk 4** is 352 of the 400 inputs of a **single legacy P2PKH transaction of 59 KB** (tx 549).
- Legacy sighash serialises and hashes the whole transaction once per input. That is ~24 MB of SHA
  for one transaction.
- It costs **114 M cycles** under GHOST + batch + tx-once, against ~38 M for a normal chunk.
- The cost packer predicts every chunk at ~212 M, because it prices signatures, not legacy sighash.
  Once signatures are cheap, the packer is wrong about exactly the chunks that matter.

**Fix.** Teach `input_costs` the legacy term (inputs × tx size) so the packer splits such a
transaction across chunks. That is host-side only and leaves METHOD_ID alone. Perfectly balanced,
the max chunk would be the mean, **~44 M against 114 M today** (derived).

# Round 3 — the whole block: chunks + aggregate (2026-10-28)

## Two more levers

**1. Aggregate parse cache.** `cached_tx` in `verify_input.cpp`, under the same `HAZYNC_TX_ONCE`.
- Every per-transaction C++ entry point now takes one `CTransaction` per distinct transaction from a
  cache: `tx_out_leaves`, `check_tx`, `tx_full_sigops`, `tx_wu_sigops`, `tx_vin_count`,
  `is_final_tx`, the lock checks, `coinbase_value` and the rest.
- The cache is keyed by (pointer, length). A hit is confirmed by `memcmp` against the stored bytes,
  so a reused buffer cannot return a stale transaction.
- The same Core functions consume the same Core type; only the number of parses changes.

- A non-witness input is charged its whole transaction's size, because legacy sighash hashes the

# Round 4 — everything, then the whole block again (2026-10-28)

## What changed

1. **Signature batch v2** (`batch_ecdsa.rs`, `hook/apply_batch_hook.py`):
   - **Schnorr is batched too.** BIP340's R = s·G + (−e)·P has ECDSA's linear shape, so a second hook
     in `schnorrsig_verify` feeds the same batch. Its own acceptance test is x(R) == r_x exactly and
     y(R) even.
   - **libsecp's internal limbs are passed directly** (8x32 LE scalars; field elements under
     patches/0012), with no byte conversion in either direction.
   - **The transcript is one contiguous hash** over the deferred tuples, and one SHA output gives two
     128-bit weights. The transcript went from ~2.7k to **~210 cycles per signature**.
   - **Signatures sharing a key are merged:** z·u2 is summed per Q before the MSM. In chunk 0, 507
     signatures use 387 keys.
2. **Aggregate cache hit guard:** the full compare became a first/last 32-byte tripwire. The key is
   (pointer, length), and risc0's default guest heap is a bump allocator that never reuses an
   address, so the key alone identifies a buffer.
3. **SwiftSync accounting in the aggregate** (`swiftsync.rs`, `HAZYNC_SWIFTSYNC`):
   - One ECMH add per created coin and one subtract per coin spent from an earlier block, instead of
     Utreexo inclusion checks and updates. The host strips the proofs from the witness.
   - Hash-to-curve hints are fully checked: y, plus a non-residue witness for every skipped counter.
   - ⛔ Cost only. There is no handover check, so this is not sound on its own.

# Round 5 — chunk plumbing: SHA stream, fast commit, lazy precompute (2026-10-28)

## What changed

1. **`HAZYNC_SHA_STREAM`** (`hook/apply_sha_stream.py` patches Core's `crypto/sha256.cpp`): CSHA256
   keeps its state in the RISC0 accelerator's layout from construction to Finalize.
   - No per-block byte swaps: the IV is swapped once and Finalize is a 32-byte copy.
   - Short writes copy inline instead of calling `memcpy`.
   - Only CSHA256's own methods change; the free `sha256::Transform` paths are untouched.
2. **`fast-commit`** (`HAZYNC_FAST_COMMIT`): the chunk journal is built as the exact words risc0's
   serde would emit (u32/bool = 1 word; `[u8; 32]` = 32 words, no length; `Vec` = length + elements)
   and committed in one call.
3. **`HAZYNC_TXDATA_LAZY`**: `PrecomputedTransactionData::Init(..., force=false)` in the tx-once
   path, which is what Core's own block validation does. BIP143 / BIP341 data is computed only when
   an input spends a witness program.

## Correctness

- The chunk journal is **byte-identical**: `4fb3e3c5…4656d`, `all_valid=1`, `binds=8006`.
- Every whole-block run exited 0, and mode 5 asserts the block valid.
- The SwiftSync ECMH total is unchanged (`5e4a508f`, adds 1,782 / subs 2,542). Every coin leaf is a
  SHA-256 through the new CSHA256, so this confirms the hasher leaf by leaf, not just in aggregate.

# Round 6 — SHA word copy, scalar maths on the coprocessor, packer refit, chunk-count sweep (2026-10-28)

## Levers

1. **SHA word copy** (`hook/apply_sha_copy.py`): the stream `CSHA256::Write` copies with aligned
   word loads and shift-combines when source and destination alignment differ.
   `CSHA256::Write` cumulative went 133.7 → 121.0 M (−9.5%). The remaining cost is per-call overhead
   on thousands of tiny writes, not the copying.
2. **libsecp trims:**
   - **The ECDSA hook moved BEFORE libsecp's scalar inverse and products.** It hands over (e, s, Q, r);
     the batch computes w = 1/s, u1 = e·w and u2 = r·w on the coprocessor. libsecp's software
     `scalar_mul_512` + `reduce_512` (18.9 M) are gone from the batched path.
   - The deferred list is reserved up front.
   - The lift_x hint table is searched as big-endian u32 words.
3. **Packer refit: ⛔ FAILED, reverted.**
   - The new constants (14k / input, 26k / sig, 3 / legacy byte) made the 16-chunk straggler **1.38**,
     worse than the old constants' 1.17.
   - Cause: chunk [2199..3017), 818 inputs heavy on multisig and large witnesses, which per-input and
     per-sig terms underprice.
   - Real per-input pricing needs a witness-size or script-type term. The whole-block figures below
     use the old constants.

**What the sweep shows**
- **Each extra chunk costs ~1–2 M cycles of chunk work:** the batch's fixed bucket work, smaller

- **The aggregate does not care in execute mode.** In proving, each chunk adds one assumption

  count mainly sets how much EXECUTION runs in parallel, and how much fixed overhead is paid.
